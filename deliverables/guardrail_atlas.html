The unified design

One gateway, one contract, two loops

Cheap, deterministic checks run on every request. A paid model or cloud service is called only when a request looks borderline. Offline, a red-team loop keeps hardening the same rails.

Current shape vs. recommended backbone

Infosys Toolkit vs. NeMo Guardrails

The Infosys toolkit has the right shape - one dispatcher fanning out to ~15 checks with a single verdict - but adopting it as built means running an entire microservice mesh. NeMo Guardrails gets the same shape from one Python package.

Infosys Toolkit - right shape, wrong build

  • Deploying it as designed means standing up about 20 independently-versioned FastAPI microservices plus an Angular front end, each with its own model weights
  • Red-team modules are marked retired for release 2.2.1; the front end still ships orphaned red-team screens pointing at nothing
  • No accuracy numbers exist anywhere for its in-house fine-tuned models
  • The core dispatcher wraps each check in a broad try/except that logs and returns None - one timeout silently drops a check instead of failing loudly
  • Every one of the ~20 services must be configured with every other service's URL

NeMo Guardrails - recommended backbone

  • One pip-installable Python package, not a service mesh to operate
  • Already a plugin architecture: every rail is a self-contained module (an actions file, a config schema, a manifest) - AFNI's own detectors plug in as first-class rails
  • Ships ready adapters for about 20 managed safety vendors plus Azure services, so AFNI stays Azure-first without being locked in
  • NVIDIA-maintained with a 383-file test suite, and it publishes honest numbers about its own weak spots
Carry over from Infosys, build explicitly on NeMo
  • Per-tenant threshold service
  • One consolidated verdict
  • Fail-loud, fails-closed policy

How they connectTreat the two halves as one closed loop with four concrete hand-offs, all of them automated. First, the attack corpus becomes the test suite. PyRIT, garak, DeepTeam and promptfoo each generate adversarial inputs and score whether the target complied. AFNI should export those generated prompts, together with the scored verdict, into a single versioned regression corpus in git, tagged by tenet and by OWASP LLM Top 10 category. That corpus is the asset, not the tool: it survives any future tool swap. Second, every finding becomes a named guardrail requirement. A jailbreak that got through is not just a report line, it is a ticket against a specific rail in NeMo Guardrails, a threshold change in LLM Guard, or a new blocklist entry, and it is closed only when the same input is replayed and blocked. Third, CI gates the deploy. The pipeline runs three tiers on every pull request touching prompts, rails, thresholds or model versions: a fast deterministic tier of a few minutes (DeepEval and promptfoo deterministic assertions, PyRIT regex output scorers, replay of the frozen corpus of previously-fixed attacks, which must be 100 percent blocked or the build fails); a medium tier on merge to main of roughly 30 to 60 minutes (a promptfoo redteam run over the OWASP-mapped plugin set plus a garak probe subset, gated on a maximum attack-success rate rather than zero findings, since zero is not achievable); and a slow nightly or pre-release tier (full PyRIT Crescendo, TAP and PAIR multi-turn attacks, DeepTeam agentic vulnerabilities, and Deepchecks drift and data-quality suites). Findings from the medium and slow tiers land as tickets; regressions in the fast tier block the merge outright. Fourth, and most often skipped: test the guardrails, not just the model. garak's shields up and shields down probes are pointed at AFNI's own gateway to confirm the rails actually fire, and PyRIT's scorer_evaluation tooling with Krippendorff's alpha is run against a human-labelled sample of production traffic each quarter so AFNI can state a measured precision and recall figure for each detector instead of a vendor claim. Every result from every tier is written in the OpenGuardrails Verdict schema, so a red-team finding, a CI failure and a live production block are all the same record shape and can be trended on one dashboard. The whole loop is what AFNI shows a client reviewer: here is the attack corpus, here is the gate, here is the measured detector accuracy, here is the trend.

Build plan

One build, no phases

All twenty-six work items are in scope now, grouped by the kind of work each one is. The only ordering that matters is the runtime cost cascade — free and deterministic checks on every request, local models when a cheap check is unsure, paid calls last — and that is a per-request decision, not a date.

7 items
The runtime gateway

Everything that sits in a live request path. Ordered by cost, not by date.

  1. Stand up a single internal Responsible AI gateway as a Python FastAPI service running NeMo Guardrails (Guardrails-develop), with the jailbreak rail's fail-open default explicitly flipped to fail-closed for client-facing traffic.
  2. Adopt the OpenGuardrails GuardEvent and Verdict JSON schemas plus its safety/security/privacy taxonomy as AFNI's internal contract, and pin the protocol version since it is still pre-1.0.
  3. Fork llm-guard-main into an AFNI-owned repository, pin every HuggingFace model revision, and enable the free deterministic tier first: Anonymize with the Vault, Secrets, InvisibleText, Regex, plus NeMo's YARA injection rules and context-bloat heuristics.
  4. Turn on the model-based runtime tier: LLM Guard's DeBERTa-v3 prompt-injection classifier and local toxicity classifier, plus its cross-encoder NLI FactualConsistency scanner on every RAG response.
  5. Route Azure AI Content Safety in through NeMo as a second opinion on high-risk content and as the groundedness detector for regulated RAG flows, with an AFNI custom blocklist, explicitly as defence in depth rather than the primary filter.
  6. Port hai-guardrails-main's healthcare PHI regexes (ICD-10, MRN, NPI, DEA) and entropy-gated secret patterns into Presidio custom recognisers inside the Python stack, and calibrate all thresholds on real AFNI traffic rather than shipping defaults.
  7. Reimplement Rebuff's canary-token leak detection and its self-hardening attack-signature store as native NeMo rails, seeding the signature store from the baseline red-team findings.
6 items
Testing and CI

Offline work. None of this is in a request path, and none of it can be.

  1. Run a baseline red-team scan against one existing AFNI AI application using garak-main (CLI, low effort) and a promptfoo-main OWASP-mapped redteam run, and publish the results as the before picture.
  2. Wire the fast CI tier on the pilot application: DeepEval and promptfoo deterministic assertions plus PyRIT's regex output scorers, running in under five minutes on every pull request.
  3. Build the medium CI tier: a promptfoo redteam run over the OWASP LLM Top 10 plugin set plus a garak probe subset on every merge to main, gated on a maximum attack-success rate rather than on zero findings.
  4. Establish the versioned regression corpus in git: export every attack that succeeded against the pilot application, tag it by tenet and OWASP category, and make replay of previously-fixed attacks a hard gate in the fast tier.
  5. Stand up the slow nightly and pre-release tier: PyRIT Crescendo, TAP and PAIR multi-turn attacks, DeepTeam agentic vulnerability probes, and Deepchecks drift suites where licensing allows.
  6. Point garak's shields up and shields down probes at AFNI's own gateway to prove the rails actually fire, and add that check to the release gate.
2 items
Measurement

The part nobody does. Without it every accuracy claim is a vendor's word.

  1. Measure the guardrails rather than assuming them: run PyRIT's scorer_evaluation tooling with Krippendorff's alpha against a human-labelled sample of production traffic, and publish a real precision and recall figure per detector.
  2. Schedule quarterly re-benchmarking, because garak's own published detector metrics and the archived status of llm-guard-main both mean accuracy decays unless someone owns it.
2 items
Fairness and explainability

Scheduled batch jobs. One response is not a fairness measurement.

  1. Adopt fairlearn-main plus the AIF360-main MDSS and FACTS scanners for any AFNI application making decisions about people, and run them as a scheduled batch job, not a runtime check.
  2. Adopt shap-master for tabular and text model explanations and expose an explain endpoint backed by a background job, since SHAP is too slow for synchronous request handling.
4 items
Governance and accountability

The half that is not code. One item here is the last real blocker.

  1. Name one accountable owner per tenet and record the seven tenets, their owners and their current thresholds in a single governance register.
  2. Ship the audit store and dashboard: every verdict from runtime and CI written in the same schema, with OpenTelemetry traces flowing into Azure Monitor.
  3. Produce the standard client approval pack from CI artefacts: OWASP LLM Top 10, NIST AI RMF, MITRE ATLAS and EU AI Act mapped reports from promptfoo, plus the measured detector accuracy table and the audit-trail sample.
  4. Publish the AFNI Responsible AI Toolkit as an internal versioned package with a mandatory adoption gate: no AI-native application reaches production without routing through the gateway and passing the CI tiers.

The bottom line

How AFNI should think about cost, accuracy, and reliability

AFNI should spend its money where the risk is highest and use free, deterministic checks everywhere else. In practice that means running the cheap local checks on every single request, calling a paid model or cloud service only for the small slice of traffic that looks borderline, and pushing the expensive, slow, thorough work into nightly and pre-release testing rather than the live request path. No single filter should ever be the whole defence, because the independent evidence is clear that cloud content filters weaken on unusual and adversarial input, so the design is layered on purpose and every layer is allowed to be imperfect. The two rules that matter more than any tool choice are: if a check cannot run, say so and block rather than quietly letting the request through; and measure how accurate each check really is against human-reviewed examples instead of trusting a vendor's claim. Maintenance is the hidden cost that sinks most governance programmes, so AFNI should standardise on one gateway, one verdict format and one audit trail, and accept a slightly less capable tool when it means one fewer thing to keep alive. Finally, the testing half is not optional polish: the red-team corpus AFNI builds is a durable company asset that outlives any tool, and it is the single most persuasive thing to put in front of a client's security reviewer.
